## 1. Оракул — реальный оператор связи (или конформансный SMSC), никогда in-JVM мок

System-under-oracle для этого чекпойнта — **SMSC реального целевого оператора связи** (их
интеграционная лаборатория / сертификационный эндпоинт). Если доступ к лаборатории оператора
недоступен, может подставляться **конформансный SMSC** (сторонний SMPP 3.4
конформанс/сертификационный симулятор, напр. сервер из состава SMPP-конформанс тест-сьюта) — он
независим от этого кодбейза и не предполагает A-1.

**In-JVM мок SMSC (`proxy/src/test/.../MockSmsc`) ЯВНО ИСКЛЮЧЁН как оракул для этого чекпойнта —
никогда in-JVM мок:** он построен на собственном продакшен-кодеке этого репо (разделяет баги
кодека) и *эмулирует* аффинность оператора по построению (доставляет по тому сокету, который
выбрал тест), то есть предполагает ровно то свойство, которое утверждает A-1. То же исключение
покрывает jSMPP-мок (OBS-038): оба — CI-аппроксимации, не фальсификации. A-1 по-настоящему
фальсифицируем только против оператора связи, которым мы не управляем.

## 2. Предусловия

- Прокси развёрнут как `companion.reverse.mode-b` к эндпоинту оператора связи
  (`companion.reverse.mode-b.smsc.host` / `companion.reverse.mode-b.smsc.port` = хост:порт
  лаборатории оператора; Mode B дополнительно требует явного согласия
  `companion.reverse.mode-b.acknowledged=true` и стартует с WARN-баннером plaintext-режима).
  SMSC-плечо — plaintext в КАЖДОМ reverse-варианте (топология [B]: режим описывает
  интернет-плечо; SMSC-плечо — всегда доверенное plaintext-соединение), поэтому лабораторному
  развёртыванию не нужен TLS на стороне оператора связи независимо от варианта — а тестируемое
  поведение аффинности транспорт-независимо. Полный walkthrough запуска, обе упаковленные формы
  (JAR и канонический `docker run`), — в [руководстве по
  развёртыванию](../deployment-guide.md).
- Два и более тестовых ESME-клиентских соединения — любой SMPP 3.4-клиент, способный держать
  два конкурентных `bind_transceiver` и отправлять `submit_sm` на каждом (два шелла, два
  клиентских процесса). Конкретный клиентский инструмент не предписан; Kannel-песочница этого
  репо (Story 6.3) предложит такой, когда появится, но оракул — оператор связи, а не клиент.
- Согласие оператора на конкурентные бинды под ОДНИМ разделяемым тестовым `system_id` (суть A-1 —
  укажите это явно в лаб-запросе; некоторые операторы отвергают это политикой, что само по себе
  результат FAIL, см. §4).
- Захват пакетов на хосте прокси (`tcpdump -i any -w a1.pcap port <carrier-port>`) или
  собственные трассы сообщений оператора, плюс собственные средства наблюдаемости прокси:
  JSON-строки `bind_accept` / `bind_reject` (каждая называет `system_id`; reject несёт вердикт)
  и счётчики `/metrics` — на reverse-варианте счётчик принятых биндов —
  `relay_binds_unknown_total` (серия `relay_binds_accepted_total` существует только на forward),
  рядом `relay_pdus_total{direction}` и `relay_connections_closed_total{direction,reason}`.
  Полный справочник лог-событий и метрик описан в [runbooks](../runbooks.md); scrape-эндпоинт
  доступен только с loopback (в Docker-форме — внутри контейнера через `docker exec` java из
  самого образа).

## 3. Критерий PASS (явный, измеримый)

**PASS** тогда и только тогда, когда ВСЁ следующее выполняется на реальном операторе связи:

1. **Принятие мульти-бинда:** минимум **2 конкурентных `bind_transceiver` (≥ 2, одно окно, оба
   удерживаются открытыми) под ОДНИМ тем же `system_id`** — каждый получает ответ
   `bind_transceiver_resp` с `command_status = ESME_ROK (0x00000000)` — оба бинда живут
   одновременно на реальном целевом операторе.
2. **Аффинность DLR к сессии:** утверждение DLR-аффинности из §5 проходит в ОБЕИХ направлениях
   (submit на бинд A → DLR на сокете бинда A; submit на бинд B → DLR на сокете бинда B),
   минимум по 3 DLR на бинд.

Всё меньшее — FAIL (§4) или INCONCLUSIVE (§6) — никогда частичный PASS.

## 4. Критерий FAIL (явный)

**FAIL**, если ЛЮБОЕ из следующего происходит на реальном операторе связи:

1. **Отказ мульти-бинда:** второй (или любой) конкурентный бинд под тем же `system_id` отвергнут —
   не-ROK `bind_*_resp` (напр. `ESME_RALYBND` "already bound", `ESME_RBINDFAIL`) либо нет ответа
   в бинд-окне оператора.
2. **Кросс-доставка DLR:** `deliver_sm` (DLR) наблюдается на сокете НЕ ТОГО бинда (submit на
   соединении A даёт DLR на соединении B, или наоборот) — класс тихой мисдоставки (худший отказ
   REL-1).

При FAIL A-1 фальсифицирован для этого оператора: посылка stateless-дизайна (AD-9 — DLR едут по
сопряжённой паре сокетов; корреляции `message_id`→сессия, к которой можно было бы откатиться, не
существует) не выполняется. Эскалируйте в архитектуру: зафиксируйте оператора + доказательства в
реестре принятых рисков AD-9/AD-12 (`ARCHITECTURE-SPINE.md`) и оцените fallback (пиннинг
соединений per-`system_id` / режим single-bind-per-identity) — это изменение дизайна, вне рамок
v1.

## 5. Процедура проверки DLR-аффинности (фальсифицируемое ядро)

Для биндов A и B (один `system_id`, оба ROK, оба сопряжены через прокси):

1. Зафиксируйте TCP 4-tuple каждого бинда (клиентский порт на хосте прокси ↔ сокет оператора) из
   pcap — это идентичность сокета, на котором должен вернуться DLR.
2. **Submit на бинде A:** отправьте `submit_sm` с уникальным корреляционным маркером в short
   message (напр. `A1-PROBE-<timestamp>-<n>`) по соединению A. Утвердите, что итоговый
   `deliver_sm` (DLR) с этим маркером **приезжает на сокет бинда A (то же TCP-соединение, которое
   отправило), НЕ на сокет B**. Повторите ≥ 3 раз со свежими маркерами.
3. **Зеркально на бинде B:** submit по соединению B; утвердите, что DLR приезжает на сокет бинда
   B, не A. Повторите ≥ 3 раз.
4. Перекрёстно проверьте, что ни одно направление никогда не наблюдает чужой маркер (ноль
   кросс-утички).

Прокси должен БЫТЬ в пути для обоих биндов (оба соединения — плечи прокси↔оператор двух сопряжённых
пар) — утверждение прогоняет всю цепочку: legacy-клиент → сопряжённая пара прокси → аффинность
сокета оператора → DLR → та же сопряжённая пара → исходящий legacy-клиент.

## 6. Доказательства + записи

- Pcap (или трасса оператора), показывающий: обе пары
  `bind_transceiver`/`bind_transceiver_resp` ROK с одним `system_id`, и TCP-стрим каждого DLR,
  совпадающий со стримом его submit.
- Собственные логи/метрики прокси за окно прогона: две строки `bind_accept` (по одной на пару,
  каждая называет разделяемый `system_id`), `relay_pdus_total{direction}`, растущий на обоих
  плечах на каждый submit/DLR-раунд, а при любом отказе бинда — строка `bind_reject` с вердиктом
  и close-счётчики (таблица deny-поверхности в [runbooks](../runbooks.md) называет, где
  проявляется каждый вариант отказа: wire, лог или метрика).
- Таймстемпы, разделяемый тестовый `system_id`, эндпоинт лаборатории оператора, версия/коммит
  прокси.
- Вердикт PASS/FAIL, зафиксированный против этого плана (датированный) в ops-логе прогона; при
  FAIL — эскалация §4.

## 7. INCONCLUSIVE (не FAIL и не PASS)

Если оператор навязывает один-бинд-на-`system_id` **документированной политикой** (не наблюдаемым
поведением), лаборатория была сконфигурирована неверно или DLR выключены на лаб-аккаунте:
зафиксируйте блокер, почините лабораторию, перезапустите. Не отмечайте PASS без обоих пунктов §3,
наблюдаемых на реальном операторе связи.
