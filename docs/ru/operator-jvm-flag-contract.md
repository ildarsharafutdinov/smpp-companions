# Контракт JVM-флагов для оператора — единый набор флагов запуска (формы JAR + Docker)

> **Статус:** оригинал ратифицирован со Story 5.1 (2026-09-10; поправлен в тот же день); расширен
> на Docker-форму со Story 5.2 (2026-09-12); русский перевод — 2026-09-13, нормативен
> [английский оригинал](../operator-jvm-flag-contract.md) — эта страница исключительно
> документация, автоматически не проверяется · **Аудитория:** операторы, запускающие
> упакованный прокси через `java -jar` или `docker run` · **Решение владельца:** голый
> `java -jar` и exec-form ENTRYPOINT образа + эта страница — в репозитории нет launcher-скрипта,
> и никакая конфигурация запуска не содержится в манифесте jar.

Эта страница — **определение для оператора** JVM-флагов, которые обязан содержать каждый упакованный
запуск (FR-DEPLOY-1). Упакованный boot+smoke тест (Story 5.1 T5) запускает jar ровно с этим
набором, определённым как Java-константа в исходнике теста, — по правилу владельца (2026-09-10)
ни код, ни тест не читают эту страницу, поэтому держать страницу и константу в ногу —
обязанность ревью: изменение флага проходит через сторю, затрагивающую обе. Exec-form ENTRYPOINT
Docker-образа (Story 5.2 T2) содержит тот же набор дословно — ни одна из форм поставки не задаёт
собственные флаги, поэтому формы не могут разъехаться, и Testcontainers parity-строка сверяет
константу ↔ ENTRYPOINT на точное совпадение.

Запуск предполагает пиннированный JDK 25 (`java temurin-25.0.3+9.0.LTS`, `.tool-versions`):
preview-семантика зависит от точной сборки, которая пиннируется **окружением** (asdf
`.tool-versions`), а не сборкой — Gradle toolchain пиннирует только мажор 25, и намеренно нет
build-проверки версии (решение владельца, 2026-09-10: «asdf-пина достаточно, дополнительная
проверка версии jdk/jre не нужна»). Флаги идут **до** `-jar`; всё после пути к jar — обычная
конфигурация Spring/варианта (args или env), не часть этого контракта.

## Пиннированный набор

```text
java --enable-preview -XX:+UseZGC -XX:MaxDirectMemorySize=6442450944 -Djava.net.preferIPv4Stack=true -jar proxy.jar
```

Это **минимальный набор**: каждый запуск обязан содержать все четыре флага. Если добавляете любой
другой JVM-флаг (размер кучи — `-Xmx`/`-XX:SoftMaxHeapSize`, тюнинг GC, …), ТО ЖЕ добавление
обязано присутствовать в ОБЕИХ формах поставки — этом JAR-запуске и Docker ENTRYPOINT — или не
добавляться никуда: расхождение флагов между формами поставки — это ровно тот дрейф, который
запрещает FR-DEPLOY-1, а очевидный следующий параметр (размер кучи на ZGC-инстансе) — ровно та,
что молча раздвоила бы формы.

Артефакты, по одному на форму:

- **JAR:** `proxy/build/libs/proxy.jar`, собирается `./gradlew :proxy:bootJar` (безверсионное имя
  пиннировано; версия содержится в манифесте).
- **Docker-образ:** собирается `./gradlew :proxy:dockerImage` (тег `smpp-proxy:local`) из
  `proxy/src/docker/Dockerfile` — distroless `base-debian12:nonroot`, упаковывающий ТОТ ЖЕ jar
  байт-в-байт (никогда не пересобираемый) поверх jlink-рантайма, который выводит из него
  `:proxy:jlinkRuntimeImage` (набор модулей jdeps + крипто-пол). Exec-form ENTRYPOINT:
  `["/opt/jre/bin/java", <четыре флага выше>, "-jar", "/opt/proxy.jar"]` с пустым `CMD`:
  аргументы после имени образа добавляются как обычные Spring run-args — ровно как аргументы
  после пути к jar в JAR-форме.

## Зачем каждый флаг

**`--enable-preview` — критический.** Классы прокси скомпилированы с preview-фичами JDK 25 (JEP 505
`StructuredTaskScope`, стержень AD-5 — путь bind-adjudication работает на нём), и этот флаг —
**единственный критический preview-механизм** для упакованной формы: манифест jar намеренно не содержит
preview-маркировки, потому что атрибут `Enable-Preview` был доказанно инертен на пиннированном
лаунчере (temurin 25.0.3+9 читает Add-Exports/Add-Opens/Enable-Native-Access из манифестов, но
не имеет плеча `Enable-Preview`) и был выброшен поправкой владельца 2026-09-10. Запуск без
флага не деградирует — он отказывается в лоб: `UnsupportedClassVersionError`, называющий
`--enable-preview`, на первом preview-маркированном классе. Fail-closed по построению.

**`-XX:+UseZGC`** — пиннированный коллектор для этой формы развёртывания: всегда включённый,
чувствительный к латентности одиночный инстанс. Обе упакованные формы — smoke-тестируемые, и
обе smoke-тестируются на ZGC; пропуск флага оставляет JVM-дефолтный коллектор — непротестированную
GC-позу и GC-расхождение между двумя формами — ровно то, для чего существует правило одного
набора флагов.

**`-XX:MaxDirectMemorySize=6442450944`** — бюджет direct memory AD-30. Netty выделяет все буферы
SMPP PDU вне кучи; без явного потолка direct-бюджет фактически неограничен и процесс ловит OOM
при масштабе вместо деградации. Значение не самостоятельное — это ровно вывод дефолтов
поставляемого `application.yml`:

> 65536 × 64 × 1024 × 1.5 = 6 442 450 944 байт (6 GiB)

где 65536 — максимум кадра кодека (`SmppFrame.MAX_COMMAND_LENGTH`, фиксированный вход формулы),
а 64 / 1024 / 1.5 — поставляемая тройка `companion.memory`: `max-inbound-depth`,
`concurrent-pairs`, `safety-factor`. На буте AD-30 самопроверка сравнивает выведенный из yml
бюджет с этим живым потолком под `companion.memory.budget-check: fail`: запуск с превышением
**отказывается стартовать** (AD-17 fail-fast) — он никогда не предупреждает и не продолжает.
Следствие для операторов: перенастроив тройку `companion.memory`, перенастройте и этот флаг
минимум под новый выведенный бюджет (65536 × depth × pairs × factor), иначе бут откажет.

**`-Djava.net.preferIPv4Stack=true`** — прокси IPv4-only (COMP-4): read-only приемник `/metrics`
биндит литерал `127.0.0.1`, а egress — к SMSC и к IdP — обязан коннектиться по IPv4, даже когда
hostname резолвится и в AAAA. Системное свойство заставляет JDK предпочитать IPv4-стек, поэтому
dual-stack хост не может молча выдать IPv6-сокеты ни на одном плече.

## Ленивая инициализация — документированное отклонение, без runtime-защиты

`spring.main.lazy-initialization=true` **не отказывается** при старте. Решением владельца
(2026-09-10) **runtime-защиты нет**: флаг остаётся доступным, а предупреждение находится здесь, на
этой странице. Включение откладывает fail-fast-позу прокси с бута на **первое использование** —
конкретно **AD-17**-матрица startup-валидации роль×режим и **AD-30**-самопроверка бюджета direct
memory выполняются лениво, при первом касании затронутого бина, а не при запуске. Ошибочно
сконфигурированный или недообеспеченный инстанс поэтому стартует зелёным и выталкивает отказ на
первый бинд (или первый скрейп), а не на старт. Операторы, включающие lazy-initialization,
принимают это отклонение осознанно; поставляемый дефолт (без флага) держит валидацию на буте,
где находится fail-closed-поза.

## Как набор удерживается согласованным

Три держащихся-в-ногу представления ОДНОГО набора:

- **Упакованный boot+smoke** (Story 5.1 T5): запускает собранный jar как subprocess ровно с
  набором выше, из Java-константы запуска в исходнике теста
  (`PackagedBootSmokeTest.OPERATOR_JVM_FLAGS`) — исполняемое определение JAR-формы.
- **Docker ENTRYPOINT** (Story 5.2 T2, `proxy/src/docker/Dockerfile`): запускает тот же JAR с тем
  же набором, exec-form, как единственное определение запуска образа. Его совпадение с константой
  пиннировано Testcontainers-строкой
  (`DockerImageBootSmokeTest.imageEntrypointCarriesTheContractFlagSetVerbatim` — ENTRYPOINT из
  `docker inspect` ≡ `[/opt/jre/bin/java]` + `OPERATOR_JVM_FLAGS` + `[-jar, /opt/proxy.jar]`,
  плюс отсутствие env-разветвления флагов через
  `JDK_JAVA_OPTIONS`/`JAVA_TOOL_OPTIONS`/`JAVA_OPTS`/`_JAVA_OPTIONS`).
- **Эта страница**: операторский референс. Решением владельца (2026-09-10) ничто в репозитории её
  не разбирает — ни тест, ни launcher, — поэтому изменение флага есть сторя, затрагивающая
  константу, ENTRYPOINT И эту страницу, а ревьюер проверяет совпадение всех трёх (половина
  «константа ↔ ENTRYPOINT» проверяется машиной; связность страницы — обязанность ревью).
