# Справочник конфигурации — все действующие ключи `companion.*`

> **Статус:** оригинал написан в рамках Story 6.1 (2026-09-12); русский перевод — 2026-09-13,
> нормативен [английский оригинал](../configuration.md) — эта страница исключительно документация,
> автоматически не проверяется (правило владельца 2026-09-10: оракулом java-теста не может
> быть markdown-страница), поэтому согласованность «страница ↔ реальность» — обязанность ревью:
> изменение ключа проходит через историю, затрагивающую `application.yml`, конфигурационные записи
> И эту страницу · **Аудитория:** операторы, настраивающие любую из комбинаций роль×режим в любой из двух
> форм поставки · **Оракул:** поставляемый `proxy/src/main/resources/application.yml` и записи в
> `proxy/src/main/java/smpp/companion/proxy/config/` (`ProxyCompanionProperties`,
> `CompanionConfigValidator`, `MemoryBudget`) — если эта страница и код расходятся, истина в коде,
> а страница содержит ошибку.

Прокси настраивается через единое пространство имён `companion.*`, привязываемое
`@ConfigurationProperties("companion")` с **`ignoreUnknownFields = false`**: каждый существующий
ключ задокументирован ниже, а конфигурация с ошибочным или выведенным из эксплуатации ключом
**отказывается стартовать** с ошибкой биндера и ссылкой на ключ (fail-closed, AD-11). Всё, что
оператор не может указать в конфигурации, не поддерживается: management-API нет,
runtime-перезагрузки нет; вся конфигурация читается один раз при старте и после этого неизменна
(AD-8).

**Что эта страница не покрывает** (у каждого раздела отдельная страница): JVM-флаги запуска —
включая взаимосвязь `-XX:MaxDirectMemorySize` с `companion.memory.*` — описаны в
[`operator-jvm-flag-contract.md`](operator-jvm-flag-contract.md); пошаговые инструкции запуска и
параметры `docker run` — в [`deployment-guide.md`](../deployment-guide.md); JSON-события лога и
описание `/metrics` — в [`runbooks.md`](../runbooks.md); использование и настройка криптографии —
в [`cipher-allowlist-policy.md`](../cipher-allowlist-policy.md). Нигде в этой документации нет
показателей производительности (их опубликует Epic 7).

## Поставка конфигурации

Пять каналов поставки, в порядке приоритета Spring Boot (от высшего к низшему):

1. **Аргументы запуска** после пути к jar (`--companion.reverse.mode-b.smsc.host=smsc.carrier.example`).
   В Docker-форме аргументы после имени образа добавляются к ENTRYPOINT так же — один канал
   аргументов на обе формы (см. страницу контракта флагов).
2. **Системные свойства Java** (`-Dcompanion.bind.port=2776`, до пути к jar) — заметьте: эта
   позиция, по [контракту флагов](operator-jvm-flag-contract.md), — территория JVM-флагов: всё,
   что стоит до `-jar`, должно присутствовать в обеих формах поставки или ни в одной.
3. **Переменные окружения ОС**, relaxed-binding: точки становятся подчёркиваниями, дефисы
   убираются, всё переводится в верхний регистр (`companion.bind.port` → `COMPANION_BIND_PORT`;
   `companion.reverse.mode-b.acknowledged` → `COMPANION_REVERSE_MODEB_ACKNOWLEDGED`).
   Заметьте следствие AD-18: каждый ключ, содержащий секретный *материал*, — это **путь к файлу** —
   `client-secret-path`, `trust-store.path`, `cert-path`, `key-path` — поэтому не существует
   ключа-значения, к которому могла бы привязаться переменная окружения (решение владельца
   2026-09-11, «env принимается» как канал: секретное ЗНАЧЕНИЕ, помещённое в окружение, инертно
   по построению и нигде не принимается).
4. **`application.yml` рядом с jar** (`./application.yml`, `./config/application.yml`).
5. **Собственный `application.yml` jar** — низший приоритет; он поставляет значения по умолчанию
   для общих ключей ниже. Его шаблоны веток — *закомментированная документация*:
   незакомментированный ключ ветки внутри jar привязывал бы эту ветку для каждого развёртывания
   этого jar, поэтому поставляемый файл никогда не содержит живых ключей веток. Следствие для
   операторов: **каждый обязательный ключ ветки должен быть указан явно** в каналах 1–4 — у
   обязательных ключей веток нет значений по умолчанию нигде (паттерн `oidc.timeout`/
   `oidc.max-in-flight`: yml-шаблон документирует `4s`/`64` как значения для копирования, но ничто
   не подставит их за вас).

Списки привязываются через запятую в args/env (`--companion.tls.protocols=TLSv1.3,TLSv1.2`);
записи роутинга индексируются (`--companion.forward.mode-a.routing[0].system-id=carrierOne`).
Длительности содержат явную единицу (`4s`, `30s`, `10s`). Каждая ошибка ниже — это **отказ при
старте** (ненулевой код выхода) с сообщением, называющим виновный ключ, — контракт fail-fast
AD-17.

## Матрица роль × режим (AD-17) — вариант/ветка конфигурации

Один инстанс = одна роль (`forward` | `reverse`) × один режим (`A` | `B` | `C`). Вариант
кодируется **структурно**: заполните РОВНО ОДНУ из пяти mode-веток (`companion.forward.mode-a`,
`companion.forward.mode-c`, `companion.reverse.mode-a`, `companion.reverse.mode-b`,
`companion.reverse.mode-c`). Ноль веток — отказ ("no companion.<role> branch is configured —
exactly one is required (AD-17) — refusing to start."); две — отказ ("exactly one
companion.<role> branch is allowed (AD-17); found 2 — refusing to start."). Ветка [B] **reverse**
содержит TLS-настройки интернет-плеча, а **forward** открывает соединение к нему на каждую
SMPP-сессию; плечо SMSC всегда plaintext и доверенное.

| Вариант | Приемник / характер соединения                                                                             | Обязательно в ветке | Ошибочно в ветке (лишний ключ приводит к отказу) |
|---|------------------------------------------------------------------------------------------------------------|---|---|
| `forward.mode-a` | plaintext-приемник доверенного плеча; отдельное **соединение one-way TLS** на каждую сессию к reverse      | `trust-store` (содержит серверный сертификат reverse, SEC-096), `routing` (непустой allow-list, AD-29/SEC-058) | `oidc` (узел отсутствует — forward находится в доверенной сети; adjudication выполняет reverse, AD-12 с поправкой 2026-08-18), `smsc` (не требуется — соединение происходит из routing, SEC-097), `server-cert` |
| `forward.mode-c` | plaintext-приемник доверенного плеча; отдельное **соединение mTLS** на каждую сессию                       | `client-cert` (на каждый инстанс, SEC-057/FR-AUTH-3), `trust-store` (SEC-050), `routing` | `oidc`, `smsc`, `server-cert` |
| `forward.mode-b` | —                                                                                                          | — | **ЗАПРЕЩЕНО**: узла `companion.forward.mode-b` не существует (режим B — только для reverse; SEC-051 структурна, это не runtime-проверка) |
| `reverse.mode-a` | приемник интернет-плеча **one-way TLS** (предъявляет серверный сертификат, пиров не валидирует)            | `smsc` (SEC-059), `server-cert` (SEC-056), `oidc` (SEC-054) | `trust-store` (one-way TLS никогда не валидирует пиров — запись реестра принятых рисков; изолируйте приемник ACL через `companion.bind.host` или используйте режим C), `routing`, любые клиентские данные |
| `reverse.mode-b` | **plaintext**-приемник интернет-плеча; legacy-клиенты подключаются напрямую (forward-прокси не существует) | `smsc`, `acknowledged: true` (явное согласие, SEC-052), `oidc` — режим B всё равно выполняет adjudication ("plaintext + ROPC") | весь TLS-материал |
| `reverse.mode-c` | приемник интернет-плеча **mTLS**                                                                           | `smsc`, `server-cert`, `trust-store` (REQUIRE-валидация клиентского сертификата forward — никогда WANT, AD-13/SEC-050), `oidc` | `routing`, клиентские данные (сертификат предъявляет forward) |

`companion.forward.tls-contexts` (опционально) существует только у роли forward — в обоих
forward-вариантах — потому что только forward соединяется по TLS (поправка AD-29, 2026-08-26).
Роль reverse не содержит таблицы роутинга: каждый бинд маршрутизируется к единственному
настроенному SMSC-эндпоинту.

## Общие ключи — в каждом варианте, дефолты поставляются в `application.yml`

### `companion.bind.*` — собственный SMPP-приемник прокси

| Ключ | Тип | По умолчанию | Fail-fast защита                                            |
|---|---|---|-------------------------------------------------------------|
| `companion.bind.port` | int | `2775` | должен быть в [1, 65535] (SEC-055)                          |
| `companion.bind.host` | string | `0.0.0.0` | обязателен, непустой (ужесточение контроля F13)             |
| `companion.bind.adjudication-deadline` | duration | `4s` | обязателен; ноль/отрицательное — отказ (compact-ctor guard) |
| `companion.bind.pre-couple-idle-timeout` | duration | `30s` | обязателен; ноль/отрицательное — отказ (compact-ctor guard) |

`bind.host` — адрес привязки приемника (Story 3.3, F13): `0.0.0.0` = все интерфейсы (поведение до
3.3); приемник интернет-плеча (reverse A/C или прямой приемник режима B) СЛЕДУЕТ ограничить
интерфейсом, на котором он достижим.

`adjudication-deadline` — одно число с **тремя** ролями на стороне реле (намеренно один
параметр — прецедент «одно число» из F13): (1) бюджет верификатора — `RequestContext.deadline =
now + это значение`, передаётся в adjudicator бинда (Story 2.2 T7); (2) таймаут исходящего
соединения — connect к SMSC на каждый бинд содержит `CONNECT_TIMEOUT_MILLIS` = это значение
вместо ~30s Netty-дефолта (Story 4.4 T1/F10); (3) ingress-таймаут — таймаут верификатора, при
превышении которого происходит отказ (Story 4.4 T3/F14).

`pre-couple-idle-timeout` ограничивает **только окно connect→couple** (Story 4.4 T4): соединение,
не дошедшее до сопряжения за это окно, закрывается fail-closed (без ответного PDU), поэтому
принятый, но так и не сопряжённый сокет не должен бесконечно занимать слот лимита
`concurrent-pairs`. Таймер отменяется в момент сопряжения — простаивающие COUPLED-пары никогда
не затрагиваются. Это отдельный от дедлайна параметр, потому что возврат слотов —
операционная забота, не часть бюджета аутентификации; `30s` заметно выше допустимого
`companion.bind.adjudication-deadline` дедлайна 4s и сильно ниже «бесконечно».

### `companion.memory.*` — бюджет direct memory AD-30

| Ключ | Тип | По умолчанию | Fail-fast защита                                                                                                             |
|---|---|---|------------------------------------------------------------------------------------------------------------------------------|
| `companion.memory.max-inbound-depth` | int | `64` | ≥ 1 (AD-30)                                                                                                                  |
| `companion.memory.concurrent-pairs` | int | `1024` | ≥ 1 (AD-30)                                                                                                                  |
| `companion.memory.safety-factor` | double | `1.5` | конечное и ≥ 1.0 (AD-30; `@DecimalMin` плюс явный отказ на Infinity)                                                         |
| `companion.memory.budget-check` | enum `fail` \| `warn` | `fail` | неизвестные enum-токены приведут к отказу при старте; любое значение, кроме `warn` (включая отсутствие) трактуется как `fail` |

Netty выделяет все буферы SMPP PDU вне кучи; потолок direct memory — **производное** расчёта,
не заданное явно:
`MaxDirectMemorySize = SmppFrame.MAX_COMMAND_LENGTH × max-inbound-depth × concurrent-pairs ×
safety-factor`, где вход max-frame — фиксированная константа кодека/протокола SMPP 65536 (RELAY-026 — она
намеренно НЕ ключ конфигурации, так что максимум кодека и бюджет не могут разойтись). Три
настраиваемых входа — ключи выше. На поставляемых дефолтах вывод таков: 65536 × 64 × 1024 × 1.5 =
**6 442 450 944 байт (6 GiB)** — ровно значение `-XX:MaxDirectMemorySize` из
[контракта флагов](operator-jvm-flag-contract.md). **Жёсткая взаимосвязь:** при изменении —
необходима согласованность параметров под новый выведенный бюджет, иначе AD-30 live-самопроверка при
старте (`DirectMemoryBudgetStartupCheck`, безусловная для каждого варианта) сравнит выведенный
бюджет с реальным потолком JVM и — при `budget-check: fail`, дефолте — **откажет в старте**
("AD-30 direct-memory budget … exceeds the JVM's live direct-memory ceiling — refusing to start
(AD-17/AD-30)"). `warn` — явное согласие на принятый риск (паттерн режима B): баннер со
звёздочками в логе, затем старт. Никакое значение не отменяет саму проверку — она всегда проводится; настраивается только сценарий при превышении.

`concurrent-pairs` — **лимит принятых соединений** (переработка по ревью Story 3.3,
2026-08-26): каждое принятое соединение может стать бюджетированной сопряжённой парой, поэтому
`ConnectionCapHandler` использует этот параметр — принятые сверх лимита соединения принудительно
закрываются с WARN. Отдельного параметра лимита соединений намеренно нет (выведенный из
эксплуатации `bind.max-connections` исключён как дублирующий «два параметра — одно
число»).

### `companion.tls.*` — политика протоколов криптографии AD-34

| Ключ | Тип | По умолчанию                       | Fail-fast защита                                                                                                                        |
|---|---|------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------|
| `companion.tls.protocols` | список строк | `TLSv1.3`, `TLSv1.2`               | непустой, без пустых элементов, минимум TLS 1.2 (SEC-061 — использование ниже 1.2 приводит к отказу), каждый элемент поддерживается JDK |
| `companion.tls.tls12-cipher-suites` | список строк | четыре набора ECDHE/AES-GCM (ниже) | пересечение с поддерживаемыми наборами JDK-дефолтного `SSLContext` должно быть не пустым (AD-34)                                        |
| `companion.tls.tls13-cipher-suites` | список строк | три JDK AEAD-набора (ниже)         | тот же guard пересечения                                                                                                                |

Политика применяется к **каждому TLS-контексту, который строят обе роли** — приемнику
интернет-плеча reverse (A/C), отдельным соединениям forward на каждую сессию (A/C), переопределениям
`tls-contexts` по целям и клиентскому контексту IdP у reverse (линк token-endpoint ROPC). Минимум
TLS 1.2, предпочтение 1.3; дефолтный набор TLS 1.2 — ровно
`TLS_ECDHE_ECDSA_WITH_AES_256_GCM_SHA384`, `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384`,
`TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`, `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` (без CBC, без
static-RSA, без RC4/3DES); дефолтный набор TLS 1.3 — ровно `TLS_AES_256_GCM_SHA384`,
`TLS_AES_128_GCM_SHA256`, `TLS_CHACHA20_POLY1305_SHA256`. Каждый runtime TLS-контекст заново
пересекает настроенный набор с поддерживаемыми наборами этого контекста и отказывается стартовать
при пустом пересечении. Обоснование политики и границы операторской настройки (что можно
безопасно добавить или убрать и чего стоит каждое изменение) описаны в
[`cipher-allowlist-policy.md`](../cipher-allowlist-policy.md).

### `companion.metrics.*` — read-only эндпоинт Prometheus

| Ключ | Тип | По умолчанию | Fail-fast защита |
|---|---|---|---|
| `companion.metrics.port` | int | `9090` | должен быть в [1, 65535] |

Весь узел **опционален**: отсутствие означает, что эндпоинт
`/metrics` остаётся выключенным; поставляемый дефолт предполагает продакшен наблюдаемым. **Адрес
привязки намеренно не является ключом**: эндпоинт биндит литерал `127.0.0.1` — loopback IPv4 — это 
единственная защита эндпоинта, поэтому не-loopback-экспозицию нельзя ошибочно
сконфигурировать, и никакой Docker `-p 9090` не найдёт ничего слушающего. Скрейпы только GET,
точный путь `/metrics`, ничего не мутируют. Что экспонирует скрейп — перечислено в
[`runbooks.md`](../runbooks.md).

### `companion.shutdown.*` — graceful-shutdown AD-22

| Ключ | Тип | По умолчанию | Fail-fast защита |
|---|---|---|---|
| `companion.shutdown.drain-timeout` | duration | `10s` | обязателен; ноль/отрицательное — отказ (compact-ctor guard) |

После остановки приемника и отказа in-flight adjudication сопряжённые пары дренируются —
in-flight записи сбрасываются, пиры полузакрываются — пока не истечёт этот таймаут; остаток
принудительно закрывается как `SHUTDOWN_DRAIN`, поэтому пир, который никогда не полузакрывается,
не может препятствовать завершению. **Контракт оператора, не валидируется автоматически:** держите строго ниже
30-секундного потолка `spring.lifecycle.timeout-per-shutdown-phase`, который указан в yml jar —
дедлайн на уровне окна фазы позволил бы Spring разрезать обход посреди дренажа.

### Сопредельные поставляемые ключи (вне `companion.*`, для полноты)

`application.yml` jar также поставляет: `spring.main.web-application-type: none` (AD-16 —
приложение остаётся non-web, даже если web-starter утечёт в classpath),
`spring.main.banner-mode: 'off'` (stdout — чистый JSON-lines поток),
`spring.lifecycle.timeout-per-shutdown-phase: 30s` (потолок дренажа выше). Вывод тела PDU в лог возможен только на уровне TRACE и по умолчанию OFF — логгер адресуется через стандартные ключи логирования
(`logging.level.smpp.companion.proxy.relay.pdu: TRACE`); при логгировании PDU команд семейства SMPP bind, пароль не попадает в лог ни на каком уровне. Справочник логов — в
[`runbooks.md`](../runbooks.md).

## Ключи веток — ровно одна ветка на инстанс

### `companion.forward.mode-a.*` и `companion.forward.mode-c.*`

| Ключ | Тип | Обязателен | Fail-fast защита                                                                                                                  |
|---|---|---|-----------------------------------------------------------------------------------------------------------------------------------|
| `<branch>.trust-store.path` | string (путь к файлу) | да | 5-состоянийная PKIX-загрузка — см. подпункт `TrustStore` ниже                                                                     |
| `<branch>.trust-store.password` | string | нет (nullable) | допускается `KeyStore.load` при отсутствии                                                                                        |
| `<branch>.client-cert.cert-path` | string (путь к файлу) | только mode-c | файл читается (SEC-060); PEM-разбираемость — eager-загрузка TLS-фабрики при init бина                                             |
| `<branch>.client-cert.key-path` | string (путь к файлу) | только mode-c | файл читается (SEC-060); там же                                                                                                   |
| `<branch>.routing[i].system-id` | string | да, на запись | непустой; **уникален** по таблице (allow-list, AD-29 — дубликат даёт отказ)                                                       |
| `<branch>.routing[i].host` | string | да, на запись | непустой                                                                                                                          |
| `<branch>.routing[i].port` | int | да, на запись | [1, 65535]                                                                                                                        |
| `<branch>.routing[i].tls-context-id` | string | нет | если присутствует, обязан ссылаться на существующий ключ `companion.forward.tls-contexts` — висячий id даёт отказ (SEC-098/AD-29) |

Таблица роутинга — это **allow-list** `system_id`, отображающий каждый разрешённый id на
единственную цель egress (AD-29: v1 — 1:1; `host`:`port` каждой записи — это reverse-прокси, к
которому соединяется forward). Бинд с `system_id` вне таблицы отклоняется fail-closed (маршрута
по умолчанию нет, AD-11). Таблица неизменна после старта. Клиентский сертификат mode-c — **на
инстанс** (один сертификат на runtime-инстанс, FR-AUTH-3 — никогда не разделяемый golden-image
ключ); ротация — передеплой.

### `companion.forward.tls-contexts.*` (опционально, только роль forward)

Map `id → клиентский cert+key`: `companion.forward.tls-contexts.<id>.cert-path` и
`companion.forward.tls-contexts.<id>.key-path`, оба — обязательные пути к файлам (SEC-060).
`tls-context-id` записи роутинга выбирает один; запись без него использует инстансный дефолт
(собственный клиентский сертификат mode-c; trust-only в mode-a). Область — forward, потому что
при топологии [B] по TLS соединяется только forward (поправка AD-29, 2026-08-26 — прежнее
расположение верхнего уровня `companion.tls.contexts` выведено из эксплуатации, см. ниже).

### `companion.reverse.mode-a|mode-b|mode-c.*`

| Ключ | Тип | Варианты | Fail-fast защита                                                                                                                                                                  |
|---|---|---|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `<branch>.smsc.host` | string | a, b, c | обязателен, непустой (SEC-059)                                                                                                                                                    |
| `<branch>.smsc.port` | int | a, b, c | [1, 65535]                                                                                                                                                                        |
| `<branch>.server-cert.cert-path` / `.key-path` | string (пути к файлам) | a, c | читаемые файлы (SEC-056/SEC-060); PEM/ключ-разбираемость — eager-загрузка TLS-фабрики при init бина                                                                               |
| `<branch>.trust-store.path` / `.password` | см. `TrustStore` ниже | c | 5-состоянийная PKIX-загрузка — якорь REQUIRE-стороны (SEC-050)                                                                                                                    |
| `<branch>.acknowledged` | boolean | b | обязан быть `true` для старта — "companion.reverse.mode-b (plaintext) requires explicit opt-in (companion.reverse.mode-b.acknowledged=true) — refusing to start (SEC-052/AD-17)." |
| `<branch>.oidc.*` | см. ниже | a, b, c | см. подпункт OIDC                                                                                                                                                                 |

Режим B (`acknowledged: true`) стартует с WARN-баннером — текст цитирует
`CompanionModeBWarning` дословно в [руководстве по развёртыванию](../deployment-guide.md);
принятый риск, на который он указывает, — использование plaintext SMPP-паролей на интернет-плече. Режим A стартует
с аналогичным `CompanionModeAWarning` (one-way TLS: reverse не может аутентифицировать
подключающийся forward — изолируйте приемник ACL или используйте режим C). Оба баннера являются
JSON-lines stdout одиночными WARN-строками (со Story 5.1 T3).

### Подпункт `TrustStore` (каждый trust-store ключ, все варианты)

`path` обязателен, `password` опционален. Хранилище должно загрузиться как настоящее trust store
во время старта — 5-состоянийная матрица PKIX-отказов: пустой путь / не путь / отсутствует /
каталог / нечитаем / пустой (ноль байт) / неверный формат или неверный пароль / ноль записей
`trustedCertEntry` — каждый приводит к отказу при старте (SEC-050, сообщение называет путь; **PKCS12
ожидаем на JDK 9+ — JKS не поддерживается**). Trust store **никогда не откатывается на дефолтный JDK
`cacerts`** (AD-13/AD-26): используйте минимальное узкоспециализированное хранилище с сертификатами
вашего issuing-CA. Доверие публичному PKI для пира — явное согласие с предупреждением,
никогда дефолт; запись runbook описана в [`runbooks.md`](../runbooks.md).

### Подпункт `oidc` (каждый вариант reverse — единая точка проверки до SMSC)

| Ключ | Тип | По умолчанию | Fail-fast защита |
|---|---|---|---|
| `<branch>.oidc.provider-url` | URI | — (обязателен) | схема https + host (SEC-053/054 — безхостовые и `http://` дают отказ); не-URI строка отказывается при конверсии бинда |
| `<branch>.oidc.client-id` | string | — (обязателен) | non-null, непустой |
| `<branch>.oidc.client-secret-path` | string (путь к файлу) | — (обязателен) | читаемый файл (SEC-060/AD-18) — единственная аутентификация клиента перед провайдером |
| `<branch>.oidc.trust-store.path` / `.password` | см. `TrustStore` | path обязателен | читается + загружается (AD-13: никогда `cacerts`) |
| `<branch>.oidc.timeout` | duration | — (обязателен; yml-шаблон документирует `4s`) | **валидируется**: включительно [2s, 5s] (PERF-3) И ≤ `companion.bind.adjudication-deadline` — вне окна или выше дедлайна даёт отказ (со Story 4.4 T5) |
| `<branch>.oidc.max-in-flight` | int | — (обязателен; yml-шаблон документирует `64`) | ≥ 1 (AD-28(4)) |

Принятые соглашения (зеркально `application.yml`):

- **Token endpoint выводится, а не дискаверится** (Story 3.4 T9, 2026-08-29). Прокси не делает
  **ни одного wire-вызова провайдера при старте** — документ дискавери не загружается, проверка
  issuer не выполняется. Token endpoint выводится как
  `<provider-url>/protocol/openid-connect/token`, поэтому `provider-url` ДОЛЖЕН быть **базовым
  realm Keycloak URL** (напр. `https://idp.example.com/realms/smpp-companions`), а не корнем хоста
  провайдера; ключей переопределения эндпоинтов нет. Окончание на один `/` допускается.
- **Adjudication только JWT** (Story 3.4 T1, 2026-08-27). Token endpoint обязан выпускать JWT
  access-токены: 200-ответ с не-JWT (opaque) токеном приводит к отказу fail-closed
  (`DenyIndeterminate` + WARN, называющий политику); ветки fallback нет. Ремедиация — на стороне
  провайдера: настройте client/realm выпускать JWT access-токены (пиннированный Keycloak ≥26.7.0
  выпускает JWT по умолчанию; см. раскрытие доверия в руководстве по развёртыванию).
- **TLS как единственный фактор доверия** (Story 3.4 T2, 2026-08-27). Локальной верификации
  подписей JWT и кэшированных ключей провайдера не проводится — валидное TLS соединение к
  провайдеру и есть единственный фактор. Ранее реализованный ключ (`jwks-cache-ttl`) выведен
  из эксплуатации; конфиг, всё ещё содержащий его, отказывается стартовать.
- **Direct Access Grants — предусловие оператора.** ROPC (password grant) настраивается на клиенте
  и **OFF по умолчанию начиная с Keycloak 26.2** — включите его на клиенте, иначе **бинд** завершается как fail-closed с записью в лог
  `OPERATOR_WARNING` с указанием token endpoint и `provider-url`. Прокси не делает
  startup-проверки URL; первый бинд — место, где проявляется эта ошибка.

`timeout` — бюджет HTTP на один round trip к провайдеру; `max-in-flight` — потолок
**конкурентных** adjudication: бинд, приходящий, когда все пределы достигнуты, завершается fail-closed (`DenyIndeterminate`) без всякого wire-вызова. Это порог отказа, не очередь: ожидание не реализовано. Необходимо указывать с запасом выше ожидаемой интенсивности биндов, чтобы превышение
означало stall провайдера, а не нормальную нагрузку. Информация об удалении самого ROPC
(RFC 9700 / статус OAuth 2.1, требование пиннирования сборки Keycloak) — [раздел
доверия](../deployment-guide.md) руководства по развёртыванию.

## Выведенные из эксплуатации ключи — явный отказ

Несмотря на `ignoreUnknownFields = false`, конфиг, всё ещё содержащий любой
из ключей ниже, приводит к **отказу при старте**, а ошибка неизвестного поля указывает на ключ
(семейство "… does not exist", закреплённое config-matrix-тестами). Выведение из эксплуатации каждого из ключей было
намеренным упрощением.

| Выведенный ключ | Было | Выведен | Преемник as-built |
|---|---|---|---|
| `companion.role` | ключ выбора роли (вариант теперь выбирает путь ветки) | Story 1.3 (2026-08-04) | `companion.<role>.<mode>.*` — вариант ЕСТЬ путь |
| `companion.bind.max-connections` | лимит принятых соединений | переработка чекпойнта Story 3.3 (2026-08-26) | `companion.memory.concurrent-pairs` (одно число: вход бюджета = лимит) |
| `companion.tls.contexts` | map переопределений клиентских сертификатов верхнего уровня | переработка чекпойнта Story 3.3 (2026-08-26, поправка AD-29) | `companion.forward.tls-contexts` (область forward — по TLS соединяется только forward) |
| `<branch>.oidc.client-mtls-keystore` | ветка аутентификации провайдера mTLS RFC 8705 | pre-release, 2026-08-19 (Story 3.2, поправка 5) | нет — `client-secret-path` единственная аутентификация клиента перед провайдером |
| `<branch>.oidc.client-credential-path` | прежнее имя ключа пути client-secret | pre-release переименование (Story 3.2) | `<branch>.oidc.client-secret-path` |
| `<branch>.oidc.jwks-cache-ttl` | ключ бюджета TTL кэшированного JWKS | Story 3.4 T2 (2026-08-27) | нет — кэшированных ключей провайдера не существует (TLS как единственный фактор доверия) |

Если отказ называет ключ, который вы не писали, ищите env-переменную или внешний слой
`application.yml`, оставшийся от прежнего развёртывания — имя ключа в ошибке — это путь, каким
его увидел биндер.
