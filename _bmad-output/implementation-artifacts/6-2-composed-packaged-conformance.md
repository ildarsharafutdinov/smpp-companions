## Intent

**Problem:** The product's flagship deployment topology has never run composed, end to end, as real applications. Every automated row today exercises exactly ONE proxy instance: the relay conformance suites, the TLS loopback e2e (`TlsModesLoopbackE2eTest` — two relay harnesses, AlwaysAllow verifier, no Spring context, no adjudication), and the packaged smokes (`PackagedBootSmokeTest`, `DockerImageBootSmokeTest`, `DockerSecretsE2eTest` — all reverse.mode-b, immediate-allow stand-in). The catalog's only E2E row — **E2E-001**, P1, "the sole coverage of the product's composed integration" per the spine's AD-24 composed-integration note — carries **no Status marker**. Three standing debts compound this: the two Docker suites duplicate a ~200-line `DockerRig` inner class that has already drifted (deferred-work BH7 — "consolidate into `testsupport/` before the NEXT consumer"); the packaged-shape journey matrix stops at the reverse-B allow path + startup refusals (5.2 close-out #1 — "mode A/C cells and auth-DENY journeys have no e2e row in EITHER shape", a gap `docs/deployment-guide.md` §"What is machine-proven about these shapes" states verbatim and names THIS story to resolve); and ROPC adjudication has never crossed a real TLS leg inside a composed chain (3.3 close-out entry: "loopback e2e uses the AlwaysAllow stand-in on the reverse" — still open, no marker).

**Approach:** (1) **Fold the rig first** — consolidate `DockerRig` + its launch/`cellArgs`/`awaitStartupSummary`/`assertRokBindResp`/probe helpers from the two 5.2 suites into `testsupport/` (the 4.2-fixture precedent: one public-final-class home, static factories, caller-owned handles, BEFORE the third consumer — never after), reconciling the recorded T3/T4 drift; refactor-only, both suites re-pointed, zero row/literal change. (2) **Land E2E-001 as two rungs of one composed journey**, satisfying both the row's letter (in-JVM instances) and the spine's letter (real processes, deploy-time contract, DEP-1): the **in-JVM rung** boots TWO real full-Spring-Boot application contexts in one JVM — `forward.mode-c` + `reverse.mode-c` per the AS-BUILT [B] topology (the forward dials the reverse per SMPP session over the Mode C mTLS leg; the REVERSE — not the forward — ROPC-adjudicates via the real `RopcBindCredentialVerifier` against the TLS token stand-in; the reverse dials the in-JVM `MockSmsc`; a jSMPP 3.0.2 ESME drives the legacy leg as the independent client) — and the **packaged rung** runs the identical journey on the deploy shapes: two `java -jar` subprocesses under the operator flag set with file-path secrets (AD-18/DEP-1), plus a two-container Docker leg through the folded rig (the third consumer). Journeys per rung: the **allow round** (bind ROK at the ESME; the bind frame reaches `MockSmsc` verbatim, AD-14; `submit_sm` byte-intact through both hops; the DLR returns on the originating pair — A-1 affinity across TWO proxies), the **in-session auth-DENY round** (the stand-in answers 401 → ONE generic failure code on the wire per AD-33, no couple anywhere, rich verdict only in the reverse's logs/metrics), and the **REL-3 observation** (SIGTERM/`docker stop` to each packaged instance → the ordered AD-22 drain → exit 143). (3) **Execute the journey-widening decision** per the ratified default (composed Mode C + auth-DENY in both shapes; mode A stays on the loopback suite + the parity argument, recorded explicitly — see Decisions) and **true the operator docs**: the deployment guide's machine-proven section reflects the new matrix and gains the conformance-run instructions its 6.1 text promised (`docs/deployment-guide.md:33`, `docs/README.md:31`). (4) **Close out** — dated catalog markers on E2E-001/DEPLOY-005 (technique notes recording the as-built substitutions), ledger resolutions (BH7, journey-widening, the 3.3 ROPC-through-TLS entry), `epic-6-context.md` regenerated — the COMP-1/REL-3 finals stated on the evidence.

## Design Notes

- The two-rung shape is the reconciliation of the source conflict, not gold-plating: the catalog row's tooling line says "two in-JVM proxy instances", the spine's AD-24 note says "real Spring Boot processes … also validates DEP-1" — the in-JVM rung is the row's letter (and the cheap everyday biter), the packaged rung is the spine's (and the conformance heavyweight that makes the DEP-1/REL-3 claims honest). Neither rung substitutes for the other; do not collapse them.
- The composed DELTA over `TlsModesLoopbackE2eTest` is precise: full application contexts (config records binding from args, validators, banners, `VerifierWiringConfig`'s real adapter, the metrics endpoint) + real adjudication through a real TLS leg + the two-process/two-container reality. Say this in the suite javadoc so a future reader doesn't mistake it for a duplicate.
- The Docker leg's wiring reuses the proven portal pattern twice — the ESME hits the forward container's PUBLISHED port from the host; the forward container reaches the reverse's published port via `host.testcontainers.internal` with the reverse presenting the committed `docker-host` SAN cert (hostname verification stays ON; no new fixtures, no IP-literal null-identification escape hatch needed). If a cleaner direct network-alias leg is proposed at dispatch it must still verify hostnames or justify AD-20 explicitly.
- `TestCompanionConfigs.common()` bakes fresh bind/metrics ports per instance — exactly what a two-instance JVM needs — but also the 1/1/1.0 memory trio and the shared discovery stand-in URL: read `PackagedBootSmokeTest`'s javadoc before choosing it for a boot; the composed suites don't need the AD-30 no-fork pin (DEPLOY-015 owns that), so either path is legal — document whichever is chosen in the suite javadoc.
- The DENY round's wire literal: `ESME_RBINDFAIL` 0x0000000D is the collapse code the loopback suite's routing-miss row already pins — assert the same literal through the composed chain (one code, one family, no per-flavor drift).
- Package home for the new suites: `bootstrap/` — they boot the FULL application (the `BootstrapLifecycleTest`/packaged-rig neighborhood); `relay/` owns harness-altitude tests (`TlsModesLoopbackE2eTest`). The consolidated Docker rig lives in `testsupport/` and is consumed from `bootstrap/`.
- jSMPP-as-client on the legacy leg is the row's COMP-1 point (an independent stack meeting the forward); if the jSMPP client API fights the test shape, a raw-socket client (`RelayTestFixtures.bindRequest`/`writePdu`) is an acceptable fallback — record the substitution in the marker, keep jSMPP somewhere on the path (the row's tooling names it).
- Timeouts: two boots + TLS + containers — carry the house `@Timeout(..., threadMode = SEPARATE_THREAD)` (300s in-JVM/JAR, 600s Docker) and bounded polls with dead-process fail-fasts everywhere (`awaitStartupSummary` idiom); an unbounded await on a dead child is the classic composed-rig hang.
- Ports/hosts: never `InetAddress.getLoopbackAddress()` against a literal-bound endpoint (the BH8 dual-stack trap); every satellite on a `freePort()`; containers reach host satellites only via the portal name.
- One-task-per-conversational-step, one commit per task (repo rule). T1 is committed refactor-only; T2/T3 each land runnable-green; T4 is the close-out commit.
