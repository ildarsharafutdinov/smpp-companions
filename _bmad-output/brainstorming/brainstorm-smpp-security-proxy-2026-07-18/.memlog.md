- (insight by coach) Payoff of forward-as-is + modes: proxies are CREDENTIAL-FREE transparent relays — no password vault anywhere in the proxy tier; SMSC is sole credential authority. Only proxy secrets = TLS certs for the internet leg (proxy2 server cert all modes; proxy1 client cert in Option C). - (insight by coach) Cost of the local check: (1) REVERSES credential-free — proxy2 holds legacy password registry again -> crown-jewel/blast-radius returns. (2) Introduces THREE-POINT credential sync: legacy(sends) + proxy2(validates) + SMSC(validates) must all agree per system_id; rotation must update all three atomically; drift = false rejections at proxy2. P2 (rotation) gets HARDER not easier. Rationale is sound though: pre-filter protects SMSC from bad-cred floods / account lockout; defense in depth.

Resolves dare with third path (neither local-check nor local-rate-limit = delegate). proxy2 credential-free AGAIN (vault -> authority provider); low blast radius restored.

- (decision by user) Authority provider is ALSO the source/CA for mTLS auth (issues+validates client certs) -> UNIFIED TRUST ROOT for BOTH password-grant validation AND mTLS. In Option C both ingress factors (proxy1 client cert + password-grant) chain to the same provider.
- (insight by coach) Consequences: (a) Trust crown jewel MOVES off proxy2 onto the authority provider — compromise it = mint valid client certs AND approve any password-grant = full impersonation. Trust now concentrated on the provider (protect + make HA). (b) Revocation becomes a HARD requirement: compromised proxy1 client cert (Option C) valid until expiry unless proxy2 checks CRL/OCSP via provider. (c) HA nuance: ongoing mTLS survives provider outage (cached trust store) but new binds (password-grant) + cert issuance/revocation need provider live.
- (note by coach) Checking proxy1 mTLS-cert provisioning. Greenfield (no prior material) -> reasoning from landed design: in Option C proxy1 presents a client cert to proxy2, issued by the authority provider's CA. Lifecycle = enroll -> bootstrap -> rotate -> revoke.
- (idea by coach) Enrollment mechanisms (simplest->strongest): (1) manual CSR + install (long-lived, human-rotated - avoid); (2) ACME (RFC8555) + External Account Binding for first order, then auto-issue/rotate short-lived certs; (3) SPIFFE/SPIRE workload identity - proxy1 attests what/where it is (node/process attestation, optional TPM), gets short-lived x509 SVIDs, NO long-lived shared secret; (4) Vault/step-ca PKI agent or deploy-time bake.
- (insight by coach) THE CRUX is bootstrap: how proxy1 gets its FIRST cert before it has one. Options: EAB key (ACME), one-time join token, node/workload attestation (SPIRE), or deploy-baked bootstrap cert. After first cert, renewal is self-served (present current cert, get new).
- (insight by coach) PAYOFF: short-lived certs (hours) + auto-rotation DISSOLVES the earlier revocation 'hard requirement'. No CRL/OCSP needed - stolen cert useless in minutes; 'revoke' = 'don't renew the compromised workload'. proxy2 validates chain+expiry; authority provider refuses re-issuance to the bad node. Cleaner than revocation infra. Private-key storage sets the floor (file+perms baseline; TPM/sealed-secret for non-extractability).
- (question by coach) Which enrollment fits depends on what the authority provider exposes: ACME endpoint, internal PKI (Vault/step-ca), or SPIFFE/SPIRE? That mostly decides bootstrap too (EAB token = simple; node attestation = no long-lived secret). Lean: automated+short-lived+sidecar-managed so lifecycle is hands-off and revocation = stop renewing.
- (decision by user) proxy1 mTLS client cert = DEPLOY-TIME BAKE (provisioned at deploy/provisioning by CI/pipeline; no ACME/SPIFFE/sidecar; rotation = re-deploy). Simplest; bootstrap handled out-of-band by the bake pipeline's own credential.
- (insight by coach) Consequence: deploy-time bake -> long-lived certs -> FORFEITS the 'short-lived dissolves revocation' payoff. Revocation (CRL/OCSP) REINSTATED as a real need, OR accept the long exposure window of a stolen baked cert. Also: protect the baked key -> per-instance keys (NOT one shared golden-image key, else one image leak = all proxy1 identity), lock down bake pipeline + image distribution, key storage on proxy1 (file perms / sealed secret).
- (idea by coach) Middle ground (keeps bake simplicity, limits exposure): SCHEDULED RE-BAKE — moderate cert lifetime (7-30d) + automated re-deploy pipeline re-bakes on schedule. Stolen cert ages out in weeks not months; eases (not eliminates) revocation pressure; no runtime enrollment.
